# Atlas application audit — 31 October 2026

**Note:** This is a point-in-time audit of the original revision. Subsequent fixes are summarized in [remediation status](remediation-status.md).

**Revision reviewed:** `3b3de1e5b89c24783b414838ad273619534cb786`

**Scope:** repository-wide, risk-based static review of calculations, source ingestion, reports, persistence, access controls and resource use, plus the checks below. This is not a full penetration test, a live-data reconciliation, or a production performance profile. No business data was changed.

**Evidence labels:** **Reproduced** = executed locally; **Code-confirmed** = behavior follows directly from the cited code, but not tested against a live deployment; **Risk** = a plausible operational consequence whose frequency or impact requires measurement. P0/P1/P2 indicate suggested priority, not measured incidents.

## Executive summary

1. **P0: Access to sensitive data, mutations and expensive AI routes is not generally authenticated in the application.** KRA access was deliberately opened, but the same deployment also exposes other powerful endpoints. Determine whether an external access gateway protects *all* `/api/*` routes before relying on it. Shared CDN caching of revisioned source snapshots requires particular attention if access control is introduced.
2. **P1: The KRA cache can recompute from an expired source snapshot and label the result newly computed.** It can also keep an as-of-date-dependent result across midnight without considering the date. Dashboard renewal outcomes have a related long-lived-tab issue.
3. **P1: A Leads chart calls current pipeline stages outcomes.** Historical reports and written methodology also contain explicit definition conflicts. These do not prove that all current KPIs are wrong; the test suite passes and current canonical definitions have improved.
4. **P1: There are real silent truncation and incomplete-history risks**, including the 500-report discovery limit, 500 source-row cap, 200 filter values per field, and list queries that rely on database defaults. These affect different surfaces and should not all be described as unlimited tables.
5. **Resource priorities:** protect AI and query endpoints; avoid stale source recomputations; reduce repeated query scans and duplicate server/browser ingestion; page database records efficiently; optimize frontend bundles and media. Do not assert savings percentages until production baselines exist.

## Correctness, data and security findings

### 1. P0 — Unauthenticated API access and potential spend abuse

**Reproduced / code-confirmed.** An isolated local app returned HTTP 200 and `{"unlocked":true}` from `/api/kra/session` without credentials. `server/kra.mjs:13-16` explicitly makes KRA routes open; `server/app.mjs:39-64` mounts routes without a general authentication middleware. Examples include:

- Source sheets and row evidence: `server/app.mjs:196-223,316-345`.
- Retention follow-ups, which include member voice and observations: `server/followups.mjs:23-31,78-110`.
- AI credentials/settings, documents, raw analytical queries, chat and report-generation endpoints: `server/intelligence.mjs:609-614,867-921,938-953`. A reachable caller can attempt to change the configured key/model, query accessible data, modify/delete documents, or invoke provider-backed work. Whether a particular operation succeeds depends on deployment configuration and validation.
- Report listings, frozen evidence, report creation, notes and pinning are not generally admin-gated (`server/reports.mjs:100-124,148-163`); admin gating applies to the report editing route at lines 135-145. Sticky-note read/write routes are also ungated (`server/sticky-notes.mjs:92-145`).

`server/snapshot-response.mjs:8-10,31-42` allows a revision-addressed snapshot to be publicly cached by the Vercel CDN for a year. If sheets contain private business or member data, simply adding origin authentication is not sufficient: the cache policy and CDN authorization behavior must be reviewed together. The KRA gate's removal was intentional, so access requirements must be agreed with the owner rather than silently reversing that decision.

**Recommendation:** verify actual perimeter protection and workbook sharing first; then use authenticated identity and role-based authorization on every data, write, settings and AI route, CSRF/origin controls where applicable, audit logs, admin-unlock rate limits, request/concurrency limits and spend budgets. Make private snapshots private or use a rigorously authorization-aware cache; review retention and invalidate any exposed cache as appropriate. Test anonymous and cross-role access on the deployed edge, not only Express. Avoid storing secrets client-side. No claim of an actual breach is made.

### 2. P1 — KRA recomputation can be fresh in timestamp but stale in data

**Code-confirmed.** In `server/kra.mjs:41-55`, a normal computation reads a locally cached source even when it is older than 15 minutes; it sets `data.stale` but does not call `load` to refresh it. The result is then written with a new `computedAt`; lines 66-69 use it for 30 minutes without a revision check. Thus, after an expired result or workbook edit, a newly computed KRA can still reflect an old sheet snapshot. A forced refresh follows a different path. The extent depends on actual cache and workbook timing.

**Recommendation:** use `load(source, false)` or explicitly validate each cache revision before compute; propagate source timestamps/revisions and stale/failed state to the result and UI. Do not advance freshness or store a successful-looking result when required input is unavailable. Add a fake-clock test: old snapshot + edited workbook + expired KRA result must trigger fresh input or explicitly report stale data.

### 3. P1 — As-of calculations can be stale across a date boundary

**Code-confirmed.** KRA `compute()` passes today's Kolkata date into `kraPerformance` (`server/kra.mjs:12,53`) and the churn grace period is date-dependent (`server/kra-churn.mjs:22-29`). Yet the 30-minute result cache and the 12-hour unchanged-revision reuse (`server/kra.mjs:23-33,66-69`) do not include the as-of date. An unchanged sheet result computed before local midnight can be served after midnight, even when a grace-period state should change.

The browser materializes `renewal_outcome` when the Lapsed table is restored or ingested (`src/data/duckdb.ts:140,306-307`; `src/data/renewals.ts:24-35`). A tab left open over midnight need not re-ingest unchanged rows, so date-dependent outcomes can remain old. `analyse`'s key also excludes today's date (`src/data/analytics.ts:147-164`).

**Recommendation:** key date-dependent caches by Kolkata business date and recompute the derived outcomes at the date boundary even if source bytes are unchanged. Add clock-controlled tests around 23:59/00:00, including a member reaching the 30-day grace boundary. Keep cached source data separate from derived as-of results.

### 4. P1 — Leads chart's stage-based “outcome” conflicts with trial outcome definition

**Code-confirmed.** `src/components/Charts.tsx:321-324` labels a record “Trial completed” when its current `stage` is `trial completed`, and “Membership sold” when its stage is membership sold. Elsewhere the agent's governed instruction states trial outcomes come from `trial_status` because current stage advances (`server/intelligence.mjs:1156`); the trial metrics have corresponding tests. A person with completed trial status and a later membership-sold stage will be charted as membership sold, not as a completed-trial outcome. A row at trial-completed stage with a different trial status can be labeled completed. This is a **chart label/population conflict**, not evidence that every trial KPI is wrong.

**Recommendation:** decide whether the visual is a mutually exclusive pipeline-stage chart or an outcome chart. Rename the dimension to “Current stage” if stage is intentional, or derive trial outcomes from `trial_status` and show conversion as a separate dimension; explicitly describe overlaps. Add fixtures for progressed and inconsistent-stage leads.

### 5. P1 — Renewal methodology and historical reference disagree with current code

**Code-confirmed documentation conflict; business decision required.** The current dashboard renewal cohort uses recorded status, a 30-day churn grace period, includes frozen in the due denominator, and calculates `renewed / all due` (`src/data/renewals.ts:4-21,53-61`). KRA churn uses a different cohort: eligible Lapsed/Renewed, excludes frozen and divides lapsed by its cohort (`server/kra-churn.mjs:6-30`). These can legitimately answer different questions, but must not be presented as directly interchangeable.

`docs/report-quality-controls.md:19` instead describes renewal inferred from a later membership and a 14-day pending window. The historical Sales reference standard describes renewal as renewals divided by resolved renewals plus lapses, excluding frozen (`docs/report-reference-standards/06_Sales_and_Revenue_Performance_Kwality_House_September_2026.html`, methodology). The reference is historical material, not proof the live code uses that formula. A population with 60 renewed, 30 lapsed and 10 frozen illustrates the difference: 60% of all due versus 66.7% of resolved; neither is universally correct without a governed definition.

**Recommendation:** have the business owner approve separate names, populations, as-of/grace rules and denominators for each measure. Update the documentation and every current label/tooltip; keep historical editions clearly dated rather than silently rewriting them. Add cross-surface tests with renewed/lapsed/frozen/pending/duplicate cases and show source freshness and outcome maturity.

### 6. P1 — Cross-instance writes can overwrite each other

**Code-confirmed risk.** KRA writes serialize via an in-process promise (`server/kra.mjs:18,76-92`), then read and upsert one document (`server/store.mjs:81-90`). On separate serverless instances those queues are independent: two writers can read the same version, pass the application-side expected timestamp check, then overwrite one another. Follow-ups similarly use a local queue and read-then-upsert (`server/followups.mjs:3-14,75-111`). Report edit and presenter-note updates also read and write complete documents (`server/reports.mjs:136-155`), so overlapping writes can lose unrelated edits.

**Recommendation:** enforce optimistic version checks atomically in the database (or use row-level transactions and normalized records); return 409 on version mismatch. Add multi-instance concurrency tests with a shared database adapter. Back up and restore-test durable records. On Vercel without cloud credentials, `.floor` falls back to ephemeral `/tmp` (`server/store.mjs:43-46`); do not call that durable storage.

### 7. P2 — Filter applicability can be misleading

**Code-confirmed.** General global filters are deliberately ignored when a source has no populated field (`src/data/analytics.ts:43-47,64-74,93-95`). This avoids false zeroes, but users can mistake a cross-source figure for one filtered by instructor, category or another unsupported field. Conversely `sessionType` is applied without the field-presence guard (`lines 75-76`), which can filter an all-null source to zero. Advanced filters need a similar source-by-source applicability review.

**Recommendation:** show applied versus ignored filters on each card/table and in exports, and distinguish “unsupported/unavailable” from a true zero. Check session type consistently by source, with regression tests on multi-source views. Do not silently apply a new filtering rule without agreeing on business meaning.

## Resource and compute opportunities

These are engineering opportunities, not measured savings. Avoid removing features or changing data freshness/accuracy to achieve them.

### High priority

1. **AI tokens, API charges and CPU:** report narratives accept prompts up to 90,000 characters (`server/intelligence.mjs:609-614`), request up to 20,000 or 24,000 output tokens (`lines 672,692`); chat allows up to 24 tool/model steps (`lines 1176-1197`) and optional web search. There are per-request bounds and abort handling, but no application-level user authentication, quota or global budget found on these routes. Record provider token usage and cost per action, call count, retries and latency; add identity-based quotas, concurrency/backpressure and admin-configured budgets. Cache deterministic or identical frozen-input report work using a versioned hash, and batch only where quality tests prove equivalence. Never claim a precise token saving without telemetry.
2. **KRA source refresh:** one computation reads five sheets and normalizes their rows (`server/kra.mjs:19-27,41-55`); the code comments describe ~300k rows on cold starts, not a current measured production figure. Correct the stale-input issue first. Reuse versioned normalized facts and shared in-flight work across instances where feasible, and key as-of results separately. Measure cold vs warm latency, upstream calls, memory and freshness.
3. **Repeated analytics scans:** `performAnalysis` schedules seven base queries and additional queries for Overview and other tabs (`src/data/analytics.ts:173-271`); they execute through a serialized DuckDB queue (`src/data/duckdb.ts:77-105`). `compare === 'none'` skips previous *group* query but still computes prior aggregate and some extra prior queries. `src/report/compute.ts:142-158` similarly runs separate core and extra measure queries across the same scopes. Consolidate aggregates with shared scans/grouping sets, lazily calculate hidden panels, and skip a previous calculation only after verifying no consumer still needs it. Preserve metric definitions and compare fixture results before/after. Instrument query count, queue wait, execution time and rows/materialized bytes.
4. **Database list N+1:** report listing reads each retained report after fetching keys (`server/reports.mjs:100-110`); sticky notes fetch each document separately and filter locally (`server/sticky-notes.mjs:100-111`); each follow-up update reads the entire list before saving one row (`server/followups.mjs:5-14,75-111`). Use indexed, paginated metadata queries and row-specific updates while preserving history and authorization. Measure database requests and p95 latency with representative counts.

### Medium priority

5. **Data duplication and storage:** browser DuckDB and server agent each normalize/build facts from sheet snapshots (`src/data/duckdb.ts:245-270`; `server/intelligence.mjs:272-343`); large CSV is streamed but parsed rows are retained (`server/sheets-public.mjs:20-38,160-188`). Browser snapshots also use IndexedDB (`src/data/cache.ts`) and possibly OPFS (`src/data/duckdb.ts:202-222`). Determine actual per-user disk, peak worker/Node RSS and rebuild counts. Consider versioned normalized columnar snapshots, projection and incremental ingestion with access controls; test cold starts, provenance, schema changes, stale fallback and drill-down before changing architecture.
6. **Browser transfer and parse:** the production build emits a 2,216.64 kB minified main chunk (580.86 kB gzip), chart chunk 1,128.97 kB (379.04 kB gzip), and a 34.24 MB DuckDB WASM file (7.71 MB gzip), as reported by Vite. These are asset sizes, not proof all are downloaded at startup. `dist` is 106 MB on this checkout, including public assets; `public` is 67 MB, including 54 MB report assets. The build warns that some dynamic imports are also static and cannot create separate chunks. Audit the network waterfall, cache hit rate and route-level imports; lazy-load heavy screens and chart modules where not needed, optimize/re-encode media with quality checks, and set immutable caching for fingerprinted assets. Keep the analytical engine and visual features intact.
7. **Limits and caching:** caches in `src/data/duckdb.ts:10,77-110` and `src/data/analytics.ts:115-170` are entry-count bounded, not byte-budgeted; row-heavy results can still consume substantial memory. Add byte/row-aware limits and metrics, avoid caching large one-off raw queries, and use cancellation/debouncing for superseded requests where safe. Check invalidation, especially date changes, before extending cache lifetimes.
8. **Freshness traffic:** `src/data/loader.ts:206-220` and `server/app.mjs:192-221` already coalesce/probe and briefly share freshness data; `server/freshness.mjs:62-80` deduplicates workbook probes per instance. Measure polls per active user and Drive API usage first. Consider visibility-aware polling and jitter, but retain manual refresh and an explicit freshness SLA.

## Recommended delivery sequence and acceptance criteria

1. **Contain exposure:** inventory external access and sensitive data; agree KRA access policy; deploy identity/role checks, safe cache headers and AI quotas. Acceptance: anonymous and unauthorized API tests fail appropriately, authorized workflows still work, CDN behavior verified, spend limits observable.
2. **Restore trust in freshness and definitions:** fix KRA source validation and date-keyed caches; decide lead-stage and renewal definitions; annotate historical reference; display applied filters and source coverage. Acceptance: controlled clock/revision tests, cross-surface reconciliation fixtures, and explicit owner sign-off for changed definitions.
3. **Complete lists and protect writes:** implement pagination/truncation indicators and atomic concurrency. Acceptance: >500 reports and >200 filter values tested; exports declare population; concurrent multi-instance changes either both survive or return a conflict.
4. **Profile then optimize:** establish representative cold/warm runs and production telemetry for upstream requests, cache hits, query scans/queue time, browser worker and server peak memory, egress, database calls and model tokens/cost. Optimize the measured top contributors; compare same dataset, user journeys and freshness, with before/after p50/p95 and correctness checks. Set budgets with the owner; no performance improvement is claimed by this audit.
